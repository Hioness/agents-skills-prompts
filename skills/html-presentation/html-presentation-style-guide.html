Overview v2.1

Single-file dark HTML documents for presenting complex technical output: specs, plans, code reviews, research synthesis, prototypes. This document is the canonical implementation — every component shown can be copied as-is. Token names live in skeleton.html and in this file's :root as the single source of truth for values; behavioural and construction rules live in SKILL.md. Visual law lives here; construction and shell behaviour live in the skill text and are referenced in Writing Rules. Depth hierarchy defaults to 4 levels (--bg→--bg2→--bg3→--bg4): use 2–5 as needed.

Layout collapsible sidebar

Collapsible left sidebar — the v2.0 horizontal top bar is gone. The index is free-floating: no rail background, no separator border — the links sit directly on the page background, so the sidebar is conceptual, not a block. The rail is position: sticky at 260px; the title wraps when it is long, and the section list is vertically centered in the viewport. One click on the « toggle collapses it to a 56px slim rail that keeps the numbered index and the active-section highlight. State persists in localStorage. Layout is a grid: .shell = rail + (.content = main → footer); the content column stays centered at max-width: 960px. With no sticky top bar, scroll-margin-top drops to 1rem. Under 860px the rail becomes a static chip row above the content. SVG diagrams use .diagram-svg with min-width: 520px so they scroll horizontally on narrow screens rather than downscaling.

Export shell + collapse heuristic Rail meta is version/date only — never export buttons. Exactly one document-level export lives in the footer: copy markdown (recursive walker). Component-local copy buttons on code blocks remain allowed; they are not document export. Collapse the rail when the reading column needs room — the slim rail still shows which section is active.

Code Blocks plain by default

In v2.0, illustrative code is plain <pre><code> in var(--fg). Zero extra markup. <code> gets var(--accent) when inline. Line numbers are now opt-in — for diffs and line-referenced reviews that actually need them. The per-block copy control is component-local clipboard, not the document export.

from pathlib import Path
from typing  import Optional

# Load configuration from environment
def load_config(env_path: Path) -> Optional[dict]:
    if not env_path.exists():
        raise FileNotFoundError(f"No env at {env_path}")
    return {k: v for k, v in __import__('os').environ.items()}

Decision Documents v1.3

Components for architectural decision records, design reviews, and option comparisons. Four pieces: numbered option headers, analysis grids, demo sandboxes, and recommendation blocks.

Option headers — numbered N-way comparisons

Use .option-num (mono, accent, small) beside .option-title inside .option-header. Numbers are zero-padded: 01, 02, not 1, 2. The numbering signals these are ordered alternatives, not arbitrary sections.

01Collapsible sidebar (default)

Default for multi-section documents. 260px borderless left index with numbered sections; one click collapses to a 56px slim rail (numbers only) that keeps the active-section highlight. State persists in localStorage.

02Fixed sidebar (no collapse)

When the full rail must always be legible — long section labels, persistent status readouts. Same rail, no toggle, no localStorage.

03Single container (no rail/footer)

Appropriate for short, single-topic documents: UI prototypes, pattern galleries, quick references. Skip the full rail+footer shell.

Analysis grid — pros / cons

Two-column comparison. +/− mono glyphs as markers — they survive print and plain-text copy, unlike colored dots. Use for genuine trade-offs with real competing considerations. Don't manufacture analysis to fill the grid.

Pros

  • Both heading levels visible — no cycling blind
  • Fixed toolbar width — no layout shift on toggle
  • Trigger button doubles as state indicator
  • Pattern familiar from existing rich-text editors

Cons

  • Two clicks required — open popup, then select
  • Popup can be dismissed on accidental outside click
  • More implementation complexity than a cycle button

Demo area — sandbox container

Use for illustrated or live examples in spec and prototype documents. The DEMO label (absolutely positioned, top-left, mono uppercase) tells the reader this is an example, not output.

Recommendation — concluded judgment

Full accent border (not left-only like a callout). Signals the analysis is complete and a decision has been reached. Use once, at the end of a comparison section. Don't use for warnings or annotations — that's what callouts are for.

Recommendation

Pattern 01 (Split H1/H2) is the strongest choice. Both heading levels are always visible, the toolbar width stays fixed, and there's no cycling blind.

Pattern 02 (Cycle) is the runner-up if minimalism is the constraint — it matches the font-picker behavior and adds only a single DOM element.

Keyboard shortcut — kbd

Use kbd — --bg4 fill, --border stroke, mono. ⌘ K opens command palette. Shift + ⌘ + P runs linter.

Writing Rules 23 rules

RuleDetail
justify every elementIf removing it changes nothing for the reader, remove it.
section titles are nouns"Migration Plan" not "Migrating the Database". Action goes in the prose below the title.
rail title formatscope / document-type. E.g. zeroclaw / spec, spring-clean / audit.
one export, footer onlyExactly one document-level export: copy markdown, in the footer. Rail meta is version/date only. Never put export buttons in the rail.
no invented export flavorsDo not add print / PDF, copy link, copy prompt, copy diff, or copy JSON. Code-block copy is component-local and allowed.
markdown export is prose-firstFooter copy uses a recursive DOM→markdown walk that descends <section> wrappers. It is not lossless source. Prefer readable prose export over multi-format chrome. Fixed in v2.0: previously main.children missed headings inside sections.
no hero language in toolsDeveloper document, not a landing page. No taglines, no marketing copy.
callouts are exceptionalIf every section has a callout, none are exceptional. One per section is the ceiling. Callouts are for one annotation only.
callouts annotate; recommendations concludeA callout is a warning or aside. A recommendation block signals the analysis is done and a judgment has been reached. Don't conflate them.
badges communicate changeA badge is a state that could change. If it's static forever, it's a label — use .tag. Badge label must equal the class name.
tags have fixed vocabFixed — deliverable, temp, debate, remove, done. Label must match the class. No variants (no "new", no "✓ clean").
errors are instructionsError states say what happened and how to fix it. Never "something went wrong."
no lorem ipsumAll placeholder content must be plausible and domain-appropriate.
option numbers are zero-paddedWrite 01, 02, 03 — not 1, 2, 3.
analysis grids need real trade-offsDon't manufacture pros/cons to fill the grid. If the decision is obvious, state it as a recommendation without the grid.
focus every interactive elementAll a and button must have visible :focus-visible states using var(--focus).
aria-hide visual-only elementsCode and diff line numbers, gutter sigils (.ln, .dl-nums, .dl-gut) get aria-hidden="true".
print uses a dedicated theme (skeleton handles it)A @media print block lives once in the skeleton and handles white rendering. Never rely on the dark theme for print. Tints are 12–16% on white — 8% is near-invisible. Base 8% on dark is intentional; background compensates. See SKILL.md §Print.
respect reduced motionWrap all transitions in @media (prefers-reduced-motion: reduce) with transition: none.
clipboard needs fallback + feedbackTry navigator.clipboard.writeText, fall back to execCommand('copy'). Flash "copy failed" on failure.
diagrams scroll, never downscaleUse .diagram-svg with min-width: 520px. Narrow screens scroll horizontally.
highlight sparinglyUse .hl for at most one load-bearing phrase per paragraph. Never whole sentences.
code is plain by default (v2.0)Default illustrative code is <pre><code> in --fg. No required .kw/.fn/.str/.cmt/.num/.op spans. Per-token spans are opt-in for demos or hand-highlighted examples. Line numbers opt-in for diffs and line-referenced reviews.
